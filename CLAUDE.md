### Core Architectural Patterns

- **Custom Module (Page)** — Entity → Service → Workflows → Dual API Routes (admin + store). The storefront reads pages via `GET /store/pages/[slug]`; admin manages them via full CRUD
- **Page templates** — a page has a `template` key (`default`, `hero`, `narrow`, `contact`) chosen in the admin and returned by the store API; the storefront maps it to a layout (`src/modules/cms/page-templates`) and serves the page at `/<slug>` through a catch-all route, so a new page needs no code. Slugs may contain slashes (`guides/plant-care`); `CreatePageSchema`/`UpdatePageSchema` reject a slug whose first segment is a real storefront route (`RESERVED_FIRST_SEGMENTS` in `src/api/admin/pages/middlewares.ts`: it would save and then be unreachable). **To add a template:** build it in the storefront, register it in `page-templates/index.tsx`, then add its key and label to `PAGE_TEMPLATES` in `src/admin/lib/options.ts`. An unknown key renders the default layout, so the two can deploy in either order
- **Blog module** — `blog_post` (title, `handle`, `locale`, excerpt, HTML `content`, featured image + alt, author, `template`, `status`, `published_at`, `reading_time`, SEO fields) and `blog_category`, linked many-to-many. **A post exists once**: its `handle` is unique across languages, `locale` says which language the original text is written in, and the other languages are translations (see "Translations of pages, posts and categories" below), so there is never a second record with the same handle. A post is public when `status = published` **and** `published_at` is not in the future, so publishing with a future date schedules it; the workflow stamps `published_at` once and recomputes `reading_time` on every content save. Three things to know: (1) with the translation feature on, Medusa's `applyLocale` middleware moves `?locale=` to `req.locale` and **deletes it from the query**, so read it with `requestLocale(req)`, never from `req.query`; (2) `GET /store/blog/posts/:handle`, `/categories/:handle` and `/store/pages/:slug` answer **200 with `null`** for something missing instead of 404, because Next.js's data cache only keeps 200 responses and a 404 would leave an unpublished post or page online forever; (3) the list routes scan the published posts lightly (ids, date, category handles), page in memory and load only the requested page in full (the scan is capped at 2000), which is fine for a blog. Admin mutations call `revalidateStorefrontCache(["blog"])`. Tests: `integration-tests/http/blog.spec.ts` (`DB_USERNAME=<you> yarn test:integration:http integration-tests/http/blog.spec.ts`) and `src/utils/__tests__/blog-*.unit.spec.ts`. Medusa does not hot-load a new module: restart the dev server after pulling it, and run the migration (`yarn medusa db:migrate`)
- **Workflow Steps** — Each page operation (create/update/delete) is a Medusa workflow with compensation handlers. Translation workflows follow the same pattern (translate-text → save-translations)
- **MinIO Storage** — `MinioFileProviderService` handles bucket bootstrap on init, presigned upload URLs, public-read access, and local filesystem fallback. Works with any S3-compatible storage (Cloudflare R2, AWS S3, MinIO)
- **API Middleware** — Layered: global (`src/api/middlewares.ts`), admin-specific (`src/api/admin/pages/middlewares.ts`), store-specific (`src/api/store/pages/middlewares.ts`, `src/api/store/contact/middlewares.ts`). All use Zod v4 schemas with `validateAndTransformQuery` / `validateAndTransformBody`
- **Admin Extensions** — Custom admin routes for Pages and Blog, rich text editor (TipTap), image upload (MinIO presigned), product translation widget, the Translations box for pages/posts/categories, i18n translations
- **Translation System** — `featureFlags.translation: true` in medusa-config turns on Medusa's Translation module (translations of a record are rows in its table, one per language, plus the "Translate Product" workflow and admin widget for on-demand translation). Settings in `.env` (documented in `.env.template`): `TRANSLATION_PROVIDER` (`gemini`, `libretranslate`, `google-scraper`; `echo` only for tests), `GEMINI_API_KEY` (or the libretranslate variables), `AUTO_TRANSLATE_LOCALES` (languages to translate into, e.g. `hu,de`). `TRANSLATABLE_PRODUCT_FIELDS` / `TRANSLATABLE_PAGE_FIELDS` in a local `.env` are not read by any code
- **Translations of pages, posts and categories** — written once and translated, the way products are, instead of one record per language with a copy of the slug. The text fields of `page`, `blog_post` and `blog_category` are `.translatable()` in their models, so the Translation module stores each language as a row (`reference` = the entity, `reference_id`, `locale_code`, JSON `translations`) and registers the entity in `translation_settings` at boot (they also show under Settings → Translations). The record keeps the original, in its `locale`; a translation only holds text, so slug/handle, template, image and publishing state are shared. The admin has a **Translations box** in the page, post and category editors (`src/admin/components/translations/`): status per target language, "Translate all languages" (fills only what is missing) and an editor beside the original to proofread or write a language by hand ("Translate again" overwrites). Behind it: `/admin/content-translations/:reference/:id` (`GET` the state, `POST` save one language, `DELETE ?locale=`) and `/translate`, workflows `translate-content`, `save-content-translation` and `delete-content-translation` (with compensation), and `src/utils/translations/`: `content-types.ts` says which fields each type translates and how (text, textarea or HTML; a unit test keeps it equal to the models' `.translatable()` fields), `targets.ts` the languages and provider status, `plan.ts` + `chunk-html.ts` cut long HTML at block boundaries into requests of about 9000 characters and join the answers
  - **Serving** — `/store/pages/:slug` and `/store/blog/*` take the visitor's `?locale=`, read the original and lay the translation over it (`resolveLocalizedRecord` / `localizeRecords` in `apply.ts`): the exact locale, then the bare language, then a sibling variant (`de-AT` serves a `de-DE` visitor), then the original; a field with no translation stays in the original language. It reads the rows with the Translation module's service, not `query.graph({ locale })`, because that matches the exact locale only
  - **Pages made the old way** (one record per language with the same slug) keep working: a record written in the visitor's own language is served as it is and wins over a translation, so nothing live changes until an editor deletes the duplicate (the Translations box says when one exists). Two records with the same slug *and* language are a data mistake; the oldest wins (`pickBestRecord`)
  - **Gotchas** — the module's `updateTranslations` **merges** the JSON and cannot remove a field, so `save-content-translation` deletes and recreates the row when a value is blanked. The module keeps no link back to the record, so the delete workflows of pages, posts and categories end with `delete-record-translations` (with compensation); without it a deleted record's rows would stay behind. Translation events (`translation.created/updated/deleted`) revalidate the storefront cache (`src/subscribers/translation-revalidation.ts`: `page` → `pages`, `blog_*` → `blog`). A new `.translatable()` field needs a restart (the module syncs `translation_settings` at boot) and an entry in `content-types.ts`. Tests: `integration-tests/http/translations.spec.ts` (runs on the `echo` provider, set in `integration-tests/setup.js`) and `src/utils/__tests__/translations-*.unit.spec.ts`
- **Contact Form** — Posts to Resend (or SendGrid fallback) via `POST /store/contact` with Zod-validated body
- **Admin Invites** — Medusa emits `invite.created` / `invite.resent` but sends no email itself, so `src/subscribers/admin-user-invite.ts` emails the invitee a link to the admin's accept page (`BACKEND_PUBLIC_URL` + admin path + `/invite?token=`; without `BACKEND_PUBLIC_URL` in production the link points at localhost). It goes out as finished HTML, so the token (which can create an admin account) stays out of the notification log. Invites work for 24 hours by default (user module option `valid_duration`); an expired or lost one is renewed with "Resend invite" under Settings → Users. Test: `integration-tests/http/admin-invites.spec.ts` (needs `DB_USERNAME` when the local Postgres has no `postgres` role)
- **Build** — `yarn build` (`medusa build`, then `src/scripts/postBuild.js`) type-checks everything in `src/` and stops on a single type error, so a failed build lists the errors and `postBuild` never runs. Tests (SWC), `medusa develop` and `medusa exec` do not type-check: code can pass every test and still break the build. After changing server code run `npx tsc --noEmit` (or `yarn build`) and look only at `src/`; `integration-tests/` and `src/admin` are left out of the build, and 19 older errors in `sales-commission-commissions.spec.ts` and `sales-commission-refunds.spec.ts` do not affect it

## Sales Commission Plugin (`medusa-plugin-sales-commission`)

Salespeople are assigned to customers at a per-client rate and earn commission on every paid order (plus Level 2 for the rep who referred them). Each rep has one running balance per currency; the owner approves finished months, pays in one payment run, and reps recruit new reps by invite. It is a **separate Medusa plugin** in the sibling repo `../medusa-plugin-sales-commission` (see its README for rules, API, events and the Make.com hand-off), vendored here as a tarball (yalc for local development) and registered under `plugins` in `medusa-config.ts` (options: `timezone`, `portal_url`, `storefront_url`, `fx_auto_fetch`, `payout_day`, `invite_days`, `level2_default_rate`, `level2_default_months`; each has a `SALES_COMMISSION_*` variable in `.env.template`).

- **Trigger** — `payment.captured`. Make.com captures the Medusa payment when Billingo reports the bank transfer (`POST /admin/payments/{id}/capture`), or an admin clicks Capture. No change to `src/subscribers/order-events-make.ts` is needed
- **Voids and refunds** — `order.canceled` and a full `payment.refunded` void the commission; a partial refund takes back the refunded share with adjustments in the current month (under a per-order lock). A nightly job re-runs all of it for the last 7 days
- **Currency** — a rep can be paid in EUR or HUF; commission in the other currency is converted when earned at the ECB rate of the day, stored on the entry. A weekday job fetches the ECB rate (`SALES_COMMISSION_FX_FETCH=false` turns it off; rates can be entered under Payment run)
- **Admin** — Sales Reps (balance per rep, "Hide inactive"), Applications, Payment run and Commission report screens, plus a "Sales rep" widget on the customer page. A rep is **deleted** only when they have no money on record, no current clients or recruits and nothing waiting (`DELETE /admin/sales-reps/:id`, the "Delete rep" box on the rep page); any other rep is deactivated. A deleted rep's portal login stays in Medusa, linked to nobody, and the next rep with that email takes it over (plugin step `link-portal-auth-identity`: Medusa's own link step refuses a login that ever had a rep)
- **Recruiting** — reps invite from the portal; the candidate applies from a personal link (`/sales-portal/join/<token>`, public routes `/sales-invites/*` in the plugin); the owner approves or declines under Sales Reps → Applications. The plugin emits `sales-commission.invite.sent`, `.application.received`, `.approved` and `.declined`; `src/subscribers/sales-rep-invite.ts` and `sales-application-*.ts` turn them into the emails in `src/modules/resend/emails/Rep*.tsx` (en, de-AT, de-DE, hu-HU). These are rendered in `src/utils/rep-emails.ts` and sent as finished HTML, so the secret link tokens never reach the notification log. The owner's "new application" email goes to `SALES_COMMISSION_NOTIFY_EMAIL`, else `CONTACT_EMAIL`
- **Client link** — a rep's job is to bring clients in, so each rep has a personal link, `<storefront>/?ref=CODE`, that works on any page (home, a product, sign-up). The storefront remembers the code in a cookie and, when a *new account* is created, puts it in the customer's metadata (`sales_rep_ref`). The plugin's `customer.created` subscriber then links the client to the rep at the rep's **standard client rate** (`default_client_rate`, set when creating the rep, approving an application, or in Edit; empty keeps the link off) from the start of that day. Only a new account is ever linked: not an existing customer, not someone who already ordered or has a rep under any account with that email, not the rep's own account, nobody while the rep is deactivated or has no rate. The answer is kept once per client (`link_claim`), and a nightly job finishes any whose event was lost. `STOREFRONT_PUBLIC_URL` is the plugin's `storefront_url`, which builds the link the owner sees under Sales Reps → rep → Client link. The plugin emits `sales-commission.client.joined` and `.client.not_linked`; `src/subscribers/sales-client-joined.ts` emails the rep (their portal's language, client name only, never the client's email) and the owner, and `sales-client-not-linked.ts` emails the owner the reason; both go through `rep-emails.ts` and `src/utils/sales-owner.ts` (`SALES_COMMISSION_NOTIFY_EMAIL`, else `CONTACT_EMAIL`). A private buyer who checks out as a guest has no account and is not linked; a business buyer must create one at checkout, so is. A signed-out returning customer recognised by email makes no new account: `POST /store/carts/:id/attach-account` puts the cart on their own, so the rep they have is credited (see "Checkout accounts and customer privacy"). A quote request saves the rep's code for the owner instead (see "Delivery requests"). Rules, edge cases and routes: the plugin's README, "Client link"
- **Sales portal** — reps sign in with Medusa's own auth as the `sales_rep` actor (`/auth/sales_rep/emailpass`) and read their own numbers from the plugin's read-only `/sales-portal/*` API, called server-side by the storefront at `/<country>/sales-portal` (see the storefront's CLAUDE.md). An admin gives or ends access under Sales Reps → rep → Sales portal; the rep sets a first password with forgot-password. `PasswordResetEmail` links reps to `/sales-portal/reset-password` (`src/utils/password-reset-link.ts`). `portal_url` comes from `SALES_PORTAL_URL`, else `STOREFRONT_PUBLIC_URL` + `/sales-portal`

## Delivery pricing (shipping classes and rates)

The shop has two **shipping classes**, which are Medusa shipping profiles: **Pallet products** (`type: pallet`: larger plants and trees, one pallet per unit) and **Carton products** (`type: carton`: Rose Royal and Magnolia, one carton per unit). A product belongs to one (Product → Shipping profile in the admin). A cart pays **one delivery for every class it holds**: the storefront asks for a shipping method per profile, and Medusa refuses to complete a cart whose profiles are not all covered. So 1 Bonsai and 2 Magnolia to Austria cost the pallet price plus 2 × 50 € for the cartons.

- **Rates** — `src/modules/shipping-rates` (`shippingRates`). One `shipping_rate_table` per class and country: zones (postcode prefixes and ranges such as `8, 90, 1000-1999`; the longest match wins; one zone is the fallback that takes every other postcode, and a delivery whose postcode is not known yet) and price rows (how many units the row covers, an on/off flag, a euro price per zone). The rules are plain functions in `lib/rates.ts`, shared by the checkout, the admin's calculator and the tests: a row for exactly the quantity wins; larger quantities are built from the largest active rows first; a remainder smaller than every row uses the smallest row. A table with one fallback zone and one "1 unit" row is a fixed price per unit. `shipping_rate_currency` rows hold the exchange rate (how many units of the currency make 1 euro; forint starts as a placeholder of 400 until the real rate is entered). Figures are euro and net of VAT (`is_calculated_price_tax_inclusive: false`); the cart's currency is converted when the delivery is charged
- **Starting figures** — `lib/initial-rates.ts`: Austria and Germany pallets are Sky-Log's tariff ("Austrian and German delivery prices.xlsx"), Hungary is 50 € per pallet, cartons are 50 € per unit in all three. The sheet gives one example postcode per zone, not the postcodes a zone covers, so each example is seeded as a prefix and every other postcode falls to the dearest zone (the fallback) so nothing is undercharged: replace the prefixes with Sky-Log's full zone list in the admin. The sheet has several 1-pallet rows (by weight and height); the first is on, the others are kept switched off. After the first save the figures belong to the admin and `setup-shipping` never overwrites them
- **Charging** — `src/modules/tariff-fulfillment` is a fulfillment provider (`tariff_rates`: identifier `tariff`, registered as `rates` in `medusa-config.ts`). Its shipping options are `price_type: calculated` with `data: { id: "<class>" }`; `calculatePrice` sums the quantities of the cart items under the option's profile (Medusa already narrows them) and quotes them for the delivery country and postcode with `quoteFromStore`. Medusa's `POST /store/shipping-options/:id/calculate` passes no `currency_code` in the provider's context, so the provider reads it from the cart (`context.id`) through the cart module, which is why the fulfillment module entry in `medusa-config.ts` is `dependencies: ["shippingRates", Modules.CART]`; without it forints would be charged the euro figure. A provider that throws (no rates for the country, no exchange rate) blocks the cart refresh by design, with a message that says what is missing. The manual provider (`manual_manual`) stays registered for the old flat options
- **Admin** — the **Shipping rates** screen (`src/admin/routes/shipping-rates`, `components/shipping-rates/rate-table-editor.tsx`; truck icon in the sidebar): a card per class and country, row switches, the exchange rates and a "try it" calculator. Each save is a workflow (`save-shipping-rate-table`, `delete-shipping-rate-table`, `save-shipping-currency-rate`, `delete-shipping-currency-rate`). A price is changed there, never in code. Which destinations get which delivery options is still Medusa's own: Settings → Locations & Shipping, the stock location's delivery zones
- **Setup** — `src/scripts/setup-shipping.ts` (`npx medusa exec ./src/scripts/setup-shipping.ts`; on the server `npx medusa exec ./src/scripts/setup-shipping.js` from `.medusa/server`). Safe to run twice and after rates were edited: it makes the two classes (the class first called "Pallet product" is renamed), saves starting rates and the forint rate where there are none, links the provider to the stock location, adds a calculated "Pallet delivery" and "Carton delivery" option to every delivery zone, and puts products in a class by name (`shipping-classes.ts`: Rose Royal and Magnolia in cartons; Cherry Blossom, Bonsai, Maple, Orchid and Blue Cascade on pallets). A product matching neither keeps its profile and is logged, so give it a class in the admin. **Give every new product a class** or it is delivered at the profile it has. The old flat options ("Standard Shipping") are left as they were: switch them off for a destination that should only offer the rates
- **Translations of the delivery options** — the options and their types are Medusa records, so their German is saved as `de-DE` translation rows (the one German locale the store offers, which the storefront asks for in every German market; one text serves Austria and Germany). `src/scripts/translate-blue-cascade-and-delivery.ts` (`npx medusa exec ./src/scripts/translate-blue-cascade-and-delivery.ts`; on the server the `.js` from `.medusa/server`) finds the "Pallet delivery" and "Carton delivery" options by the code of their type and saves "Palettenversand" and "Kartonversand" with the sentence under each; the German lives next to the English in `DELIVERY_OPTIONS` (`shipping-classes.ts`), so **a new delivery option needs its German there**. Run it after `setup-shipping`: it adds only what is missing, so it is safe to run twice and never replaces a translation edited in the admin. An order keeps the name in the language the customer checked out in (the emails and the pro-forma invoice show only the shipping total)
- **Deploy** — run `yarn medusa db:migrate` (the module adds two tables), then the setup script once. Medusa does not hot-load a new module or a changed `medusa-config.ts`, so restart the dev server after pulling. On the server: `yarn install`, `yarn build`, then `cd .medusa/server`, `npx medusa db:migrate`, `npx medusa exec ./src/scripts/setup-shipping.js`, back in the backend folder `pm2 restart medusa-backend`; deploy the storefront with it, since its delivery step asks for one delivery per class
- **Tests** — `yarn test:unit src/modules/shipping-rates` (the rules); `DB_USERNAME=<you> yarn test:integration:http integration-tests/http/shipping-rates.spec.ts` (setup, the Austria, Germany and Hungary examples, mixed carts, forint charging, the calculated price equal to the charged one, a cart refused without a delivery for every class, an order placed with both deliveries, rate edits through the admin API)

## Products: metadata, price on request, notify me and video

- **Copy in metadata** — a product's metadata (Product → Metadata in the admin) holds what Medusa's own fields have no place for, each as plain text or JSON with one text per language (`{"en": "…", "de-AT": "…", "de-DE": "…", "hu-HU": "…"}`): `short_description` (shown under the title; the full description then moves to a Description section further down), `approx_dimensions` (`{"height": "160–180", "width": "140–170", "depth": "80–100", "unit": "cm"}`), `seo_title` and `seo_description` (used as written for the page's `<title>` and meta description), next to the older `key_features`, `care_instructions` and `pot`. `src/scripts/add-blue-cascade.ts` (`npx medusa exec ./src/scripts/add-blue-cascade.ts`, with `draft` to keep it unpublished) adds the Blue Cascade product with all of them (text in `src/scripts/product-content/blue-cascade.ts`), the "One of a kind" category and the pallet class; its pictures are uploaded in the admin. `translate-blue-cascade-and-delivery.ts` then gives it its German: `de-DE` translation rows for the title, badge ("Einzigartig"), description, the "Planter" option and its three values, the variants and the "One of a kind" category ("Unikate"), and German (both markets) and Hungarian next to the English in its metadata. The text is in `blue-cascade.ts`; `src/utils/localized-metadata.ts` only adds a language that is missing and leaves a text alone whose English was edited since (`yarn test:unit src/utils/__tests__/localized-metadata.unit.spec.ts`)
- **Price on request** — a product none of whose variants has a price in a market shows "Price on request" in the storefront and cannot be bought (`isPriceOnRequest()`), so a piece can be published before its price is agreed
- **Notify me** — when nothing of a product can be bought (price on request and nothing in stock) the storefront offers "notify me when available" for the product as a whole, and for a single out-of-stock variant otherwise. `POST /store/notify-me` (Turnstile-checked, see below) saves the signup in `notify_me_request` through the `create-notify-me-request` workflow, once per email, product and variant, and emails the shop as a courtesy (a missing email key or a failed send is logged and never fails the visitor). The admin lists and deletes signups under **Notify me**. Test: `integration-tests/http/notify-me.spec.ts`
- **Product video** — the **Product video** box on the product page (`src/admin/widgets/product-video-widget.tsx`) uploads a video (MP4 or WebM, up to 20 MB, to the same file storage as other media) and an optional still image, and saves them in the product's metadata as `video_url` and `video_poster` with the ordinary product update, so the storefront cache is refreshed by `product.updated` like for any product change. Medusa merges metadata and removes a key whose value is `""`, which is how a video is taken away (`src/admin/lib/product-video.ts`; a still image alone does nothing, so it goes with the video). The storefront gallery shows the video after the second product image, as the still image (the first product image when there is none) with a play button, and plays it in place. Only a file works, not a YouTube or Vimeo page, and the box refuses those links. Tests: `yarn test:unit src/utils/__tests__/product-video.unit.spec.ts` and `integration-tests/http/product-video.spec.ts`
- **Long description** — the product's own Description box stays the short plain text under the title (Translate Product translates it with the title). The formatted text of the storefront's Description section is written in the **Long description** box on the product page (`src/admin/widgets/product-long-description-widget.tsx`, with the rich-text editor the blog and pages use, one tab per language) and saved in the product's metadata as `long_description` with the ordinary product update (`src/admin/lib/product-long-description.ts`): plain HTML while only English is written, else JSON with `en`, `de` and `hu`, one German and one Hungarian text for every market of the language (a value written per market, as the product scripts do, is read and left alone until its language is edited; English must come first because it is what a language without a text shows). It lives in metadata because Medusa lays a translation only over a product's own fields (`applyTranslations` skips `metadata`), so the `metadata.*` rows that Translate Product saves are never shown by the storefront; the box has its own **Translate from English**, which calls `POST /admin/products/:id/translate-long-description` (`src/api/admin/products/`; the provider is `TRANSLATION_PROVIDER`, a long text is cut into pieces by `src/utils/translations/translate-html.ts`), puts the German and Hungarian into the editors for the person to read, and saves nothing until Save. Translate Product skips this key. Tests: `yarn test:unit src/utils/__tests__/product-long-description.unit.spec.ts src/utils/__tests__/translate-html.unit.spec.ts`
- **Duplicate** — the **Duplicate** button in the **View and duplicate** card on the product page (`src/admin/components/duplicate-product.tsx`) asks for the copy's title in a drawer and calls `POST /admin/products/:id/duplicate` (`duplicateProductWorkflow`, `src/workflows/duplicate-product.ts`), then opens the copy. The copy is always a **draft** (so the storefront does not show it until it is published), its handle is made from the title (`handleBase`/`copyHandle` in `src/utils/duplicate-product.ts`, the same rule as the admin's address preview, with `-2`, `-3` when the handle is taken), and the original is not touched. Copied: the product's own fields and metadata (video, SEO, long description), type, collection, categories, tags, sales channels, shipping class, the gallery in order, options and choices, every variant (its choices, metadata, rank, measurements, backorder and inventory settings, thumbnail) with its base prices and region prices, which pictures are tied to which variant, and the translations of the product, its options, choices and variants. **Not copied:** stock (each new variant gets an inventory item of its own, with nothing in stock), SKU, barcode, EAN and UPC (each belongs to one variant), the sale prices of price lists, and the product's translated *title*, which would name the original (translate the new title with Translate Product). Things to know when changing it: the pricing module's `price_set.prices` already leaves price-list prices out; a variant's `images` as Medusa reads it is its own pictures *plus every picture tied to no variant*, so the pictures to copy are read from each picture's `variants` (the ties) and a general picture stays general; `variant_rank` is not in the create type but is saved. The workflow reads in `load-product-to-duplicate`, creates with `createProductsWorkflow`, and `copy-product-extras` adds what the create input cannot carry (variant thumbnails and picture ties, translations) and undoes itself if it stops half way; the pure part is `src/utils/duplicate-product.ts`. Tests: `yarn test:unit src/utils/__tests__/duplicate-product.unit.spec.ts src/utils/__tests__/duplicate-product-dialog.unit.spec.ts` and `DB_USERNAME=<you> yarn test:integration:http integration-tests/http/duplicate-product.spec.ts`

- **Adding a product from a spec** — a product is written once as a JSON *spec* (`product-specs/<handle>.json`: every text in English with German and Hungarian beside it, prices per currency, options, shipping class, stock, SEO) and entered with `add-product.ts`, so entering one is a file, not a hundred clicks. The field reference is in the **add-product skill** (`~/.claude/skills/add-product/references/spec-fields.md`), the rules in `src/utils/product-spec.ts`. Run it with `npx medusa exec ./src/scripts/add-product.ts product-specs/olive-tree.json check` (on the server `npx medusa exec ./src/scripts/add-product.js /path/olive-tree.json check` from `.medusa/server`); the words after the file are `check` (read and report, **writes nothing**) and `draft` or `published` (replaces the spec's status). The last line of its output is `RESULT_JSON {…}` and a refused spec exits with 1. The skill's `scripts/product.sh <local|live> <doctor|catalog|check|add|inspect|status>` runs these commands here or on the server (on live, `add` runs the check there, takes a database backup and only then writes, and publishing needs `--yes-publish`), and its `scripts/verify-storefront.js <handle> --spec <file>` reads the product's public pages in the five markets.
  - **What it makes** — what the admin's form would, with the shop's conventions filled in: the product with its options and one variant for every combination (stock managed, no backorders; no options means the default option and variant the admin makes), a price per currency saved the way the admin saves them (a base price **and** one for each region that uses the currency), the shipping class (required: `pallet` or `carton`; the class is made if missing), categories (an existing one is found by name or handle in any capitals; a missing one is made and the check says so, with a "did you mean" for a typo), the metadata the storefront reads (`short_description`, `key_features`, `approx_dimensions`, `seo_title`, `seo_description`, `care_instructions`, `long_description`), stock at the stock location for each variant that has some, and the translations: German as `de-DE` rows (product, option, choices, variants, categories) and German and Hungarian next to the English in the metadata. A spec with no price makes a product that reads "Price on request"; no stock makes it out of stock with "Notify me"; no status makes it a **draft**, so nothing reaches the storefront before its pictures are there
  - **What it never does** — pictures and the video (uploaded in the admin: the product's Media and the Product video box), a collection, type or tag (they must exist: the check names the ones that do not), a price nobody gave (a forint price is never worked out from the euro one: that market reads "Price on request" until the owner enters it), sale prices (price lists, admin only), or overwrite anything. **Running a spec twice is safe**: a product with the spec's handle is left as it is, so what was edited in the admin is kept, and only gets the German rows and metadata languages it lacks (a field with text stays as written; a metadata text whose English was edited since is left alone). A product with the **same name under another handle** (renamed in the admin) stops the run, and a similar name is a warning, so a renamed product is not added again (`blue-cascade.json` must not be run on the live shop for that reason: its product is now "Blue Cascade Composition")
  - **The other commands** — `check-product.ts <handle>` reads a product as the storefront will and says what is wrong or still to do: status, category, shipping class and sales channel, the price per market (where it reads "Price on request"), stock, number of pictures and the video, the metadata (JSON that does not parse, a text with no German), and the German rows; exit 1 when it finds a problem. `list-catalog.ts` lists what a spec can refer to (categories with their German, collections, types, tags, classes, channels, locations, regions, currencies, products) and the German the shop already uses for badges, options, choices and categories, to keep new German consistent. `set-product-status.ts <handle> draft|published [force]` publishes a product only when the review finds no problem (no pictures, no shipping class or channel would put a broken page on the storefront; `force` overrides) and takes one back to draft.   - **Tests** — `yarn test:unit src/utils/__tests__/product-spec.unit.spec.ts src/utils/__tests__/product-review.unit.spec.ts` (the rules, with no database) and `DB_USERNAME=<you> yarn test:integration:http integration-tests/http/add-product.spec.ts` (the Blue Cascade spec and a priced two-option product end to end: region prices read back through the store API, stock, German rows, the dry run writing nothing, a second run keeping the admin's edits, the refusals, the commands)

## Delivery requests (European countries without delivery prices)

The checkout delivers only to the countries of the regions. Every other European country is listed at checkout under "Delivery on request" (the storefront's `src/lib/util/delivery-on-request.ts`), and choosing one sends a quote request instead of an order. `POST /store/delivery-requests` (body: `cart_id`, contact and address fields, `country_code`, optional `message`, `locale` and `sales_rep_ref`) runs `create-delivery-request`: the step reads the products, quantities and prices **from the cart** (an empty or unknown cart is refused), saves a `delivery_request` (`src/modules/delivery-request`, module `deliveryRequest`, status `new`/`handled`), and emails `CONTACT_EMAIL` with the customer as reply-to (`src/utils/delivery-request.ts` writes the text; a missing key or failed send is logged and never fails the customer). **The email is optional**: a request needs an email or a phone, at least one (the schema's refine answers 400 for neither); with no email the shop's email has no reply-to and says to call. `sales_rep_ref` is the sales rep client link the visitor followed: it is normalised the plugin's way (`normalizeRepCode`) and saved with the name of the active rep who has it (`sales_rep_name`, null for a code no active rep has or without the plugin), shown in the shop's email and the admin drawer. Nothing is linked, since a quote makes no account: the owner assigns the customer to the rep when the quote becomes an order. Sending again from the same cart updates its request. It has no Turnstile check because the checkout has no widget. The admin's **Delivery requests** screen (`src/admin/routes/delivery-requests`) lists them with a drawer per request, "Mark as handled" (`POST /admin/delivery-requests/:id`) and Delete (`DELETE`, soft). Migrations: the table, then `Migration20261106191630` (email nullable, `sales_rep_ref` and `sales_rep_name`): run `npx medusa db:migrate` on deploy. Tests: `yarn test:unit src/utils/__tests__/delivery-request.unit.spec.ts` and `DB_USERNAME=<you> yarn test:integration:http integration-tests/http/delivery-requests.spec.ts`

## Checkout accounts and customer privacy

A signed-out customer whose email has an account is recognised at checkout instead of being made to sign in (the storefront's CLAUDE.md, "Checkout"). Medusa itself ties a signed-out cart to the registered customer whose email is typed (`findOrCreateCustomerStep`), which is what lets the order land in their account and the commission plugin credit their rep (it matches `order.customer_id`).

- **`POST /store/checkout/account-status`** (`{ email }` → `{ has_account }`, `src/api/store/checkout/account-status`): whether the email belongs to a customer who can sign in (guest records don't count; `src/utils/account-email.ts` tries the email as typed and lowercased). Limited to **20 checks per visitor in ten minutes** (`src/utils/rate-limit.ts`, in memory, 429 beyond): the visitor is `CF-Connecting-IP`, else the first `X-Forwarded-For` (the storefront sends the visitor's address when it asks on their behalf, at Medusa's direct address). It says only what Medusa's own sign-up already tells anyone who tries a registered email
- **`POST /store/carts/:id/attach-account`** (`attach-cart-to-account` workflow): puts a signed-out visitor's cart on the account its email belongs to, reusing Medusa's `transferCartCustomerWorkflow` (which also sets the account's email and refreshes prices). Medusa does it alone only for a cart with no customer yet: once a cart has one, a corrected email keeps it on a guest record or on the account typed first, which would credit the wrong rep. A signed-in customer's cart, a cart whose email has no account and a completed cart are left alone; the answer says nothing about whether it moved
- **The privacy guard** (`src/api/store/customer-privacy/middlewares.ts`, `src/utils/customer-privacy.ts`): every `/store/carts*` and `/store/orders*` answer has its cart's or order's `customer` cut down to `id` and `email`. Medusa's store cart routes block only `orders` and `carts` from `fields` and its order routes block nothing, so before this a stranger who typed someone's email into a cart (or placed an order with it) could read that customer's name, phone, company, VAT number and saved addresses with `?fields=*customer,*customer.addresses`. It wraps `res.json`, so it holds whatever runs first and whatever is asked for. The storefront reads the signed-in customer from `/store/customers/me` and never needs more from a cart or order
- **Tests**: `DB_USERNAME=<you> yarn test:integration:http integration-tests/http/store-customer-privacy.spec.ts integration-tests/http/checkout-accounts.spec.ts`, `yarn test:unit src/utils/__tests__/customer-privacy.unit.spec.ts src/utils/__tests__/rate-limit.unit.spec.ts`

## Spam protection (Cloudflare Turnstile)

`POST /store/contact` and `POST /store/notify-me` run `requireTurnstile` (`src/utils/turnstile.ts`) before body validation. The storefront sends the widget's token in the `x-turnstile-token` header; the middleware checks it against Cloudflare's siteverify endpoint with `TURNSTILE_SECRET_KEY` and answers `403 { type: "not_allowed" }` when it is missing, refused, expired or reused.

- No `TURNSTILE_SECRET_KEY` → the check is off (local dev, tests, a half-finished deploy).
- Cloudflare unreachable, slow (10 s) or reporting a bad secret → the request goes through and a `[turnstile]` warning is logged. A visitor cannot cause that.
- A refusal is logged at info level as `[turnstile] rejected (token sent|no token): <codes>` (never the token). Every visitor is refused when the widget or the keys are wrong, and this line is where it shows.
- Tokens are single-use. The storefront's account-form server actions verify their own tokens, so no token is verified twice. The `/auth/*` routes are not behind this check.
- Tests: `yarn test:unit src/utils/__tests__/turnstile.unit.spec.ts`.
- Cloudflare's test keys let you exercise the flow locally: secret `1x0000000000000000000000000000000AA` always passes, `2x0000000000000000000000000000000AA` always fails (storefront site key `1x00000000000000000000AA`).

# 1. Check available updates

# 3. Run migrations
yarn medusa db:migrate

# 4. Build and verify
